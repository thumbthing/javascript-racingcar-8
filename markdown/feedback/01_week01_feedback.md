### Git

#### 기본적인 Git 명령어를 숙지한다

현재 내가 사용하기만 하는 명령어 `add, push, commit` 외의 명령어에 대해서 추가적인 학습하여 숙지

#### Git으로 관리할 자원을 고려한다

`package.json` 파일만 존재한다면 `node_modules` 폴더를 생성할 수 있다. 따라서 해당 파일은 `git`으로 관리를 할 필요가 없다.  
`.gitignore`로 제외할 자원을 선별

#### `package-lock.json`의 역할을 이해한다

`package.json`은 프로젝트가 필요로 하는 패키지와 버전 범위를 정의하고,  
`package-lock.json`은 실제로 설치된 패키지의 정확한 버전과 의존성 트리를 기록한다.  
이를 통해서 `node_modules`를 git으로 관리하지 않더라도 팀원들이 동일한 버전의 패키지를 설치할 수 있다.

#### `Commit message`를 의미 있게 작성한다

해당 `commit`에서 수행된 작업을 이해할 수 있도록 커밋 메시지를 작성한다. 또한 팀의 좋은 코드 리뷰 문화는 작은 커밋을 작성하는 것에서 비롯된다.

#### `Commit message`에 `issue` 또는 `pull request` 번호를 포함하지 않는다

일부 프로젝트에서는 작업을 이슈 또는 PR과 연결하기 위해서 `issue`와 `PR 번호`를 포함하기도 한다. 하지만 이러한 접근 방식은 원본 저장소의 관련 없는 이슈 또는 PR에 영향을 미칠 수 있다.

#### `PR`을 만든 후에는 닫지 말고 추가 커밋을 한다

이미 `PR`을 생성하면 변경을 위해 새 `PR`을 만들 필요가 없다.  
변경이 필요한 경우 추가 커밋을 하면 자동으로 반영된다.

### Debug

중간에 `console.log()`로 확인 가능하지만, 이는 비효율적이며 불필요한 코드가 남을 수 있다.  
debugger로 이용하면 코드 내부의 상태 값이 어떻게 변하는지, 어떤 흐름으로 프로그램이 실행되는지 이해 할 수 있다.

### Convetion

#### Naming

변수, 함수(메서드), 클래스 이름을 짓는데 시간을 투자해라.  
이름을 통해 변수, 함수, 클래스의 역할에 대한 의도를 드러내기 위해 노력해라.

#### 축약하지 않는다

의도를 드러낼 수 있다면 이름이 길어져도 괜찮다.  
축약은 혼란을 야기하며, 더 큰 문제를 숨기는 경향이 있다.  
클래스와 메서드 이름을 한 두 단어로 유지하려고 노력하고,  
문맥을 중복하는 이름을 자제하자.

#### 공백

`if, for, while` 문 사이의 공백도 코딩 컨벤션이다.
공백 라인을 의미 있게 사용한다.
  
- 문맥을 분리하는 부분에 사용
- 과도한 공백은 지양
- `space`, `tab`을 혼용하지 않는다

#### 주석

의미 없는 주석을 달지 않는다.
변수 이름, 함수(메서드)를 통해 어떤 의도인지가 드러난다면 굳이 주석을 잘지 않는다.  
모든 변수와 함수에 주석을 달기보다는 이름을 통해 의도를 드러내고, 그렇지 못할 경우에 주석으로 표현한다.

#### formating

IDE의 코드 자동 정렬 기능을 사용하면 깔끔한 코드를 볼 수 있다.

VSCode: ⇧⌥F, Shift+Alt+F

#### JavaScript API를 적극 활용

함수(메서드)를 직접 구현하기 전에 API에서 해당 함수를 제공하는지 확인힌다.
